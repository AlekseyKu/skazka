# 📋 План разработки проекта "Портал в Сказку"

## 🎯 Цель проекта

Создание Telegram Mini App для бота "Портал в Сказку" с современным веб-интерфейсом, который расширит возможности пользователей и улучшит пользовательский опыт.

## 📊 Текущее состояние

### Реализовано
- ✅ Telegram бот на aiogram 3.10.0
- ✅ Генерация сказок через OpenAI GPT
- ✅ Озвучка через Yandex SpeechKit
- ✅ Система подписок (free, gold, extended, premium)
- ✅ Система монет
- ✅ SQLite база данных
- ✅ FSM состояния для диалогов
- ✅ Структура подменю в боте

### Основной функционал
- Генерация сказок по теме
- Именные сказки
- Случайные сказки
- Сказки на ночь
- Коллекция пользователя
- Управление подпиской и монетами

## 🛠 Технологический стек

### Backend API
- **FastAPI** 0.115+ - современный асинхронный веб-фреймворк
- **SQLAlchemy** 2.0+ (async) - ORM для работы с БД
- **Alembic** - миграции базы данных
- **PostgreSQL** - основная БД (SQLite остаётся только как legacy-справка)
- **Pydantic** v2 - валидация данных и сериализация
- **python-jose** + **passlib** - JWT аутентификация
- **AsyncPG** - асинхронный драйвер PostgreSQL
- **python-dotenv** - управление переменными окружения

### Frontend (Mini App)
- **React** 18.3 - UI библиотека
- **TypeScript** 5+ - типизация
- **@twa-dev/sdk** - интеграция с Telegram WebApp API
- **TailwindCSS** - стилизация
- **TanStack Query (React Query)** v5 - управление состоянием сервера
- **React Hook Form** - работа с формами
- **Zod** - валидация форм (совместим с React Hook Form)
- **Vite** - сборщик и dev-сервер

### Infrastructure
- **Docker** & **Docker Compose** - контейнеризация
- **Nginx** - реверс-прокси и раздача статики
- **PostgreSQL** в Docker - база данных

### Дополнительно (опционально)
- **Zustand** - глобальное состояние (добавить при необходимости)
- **Redis** - кеширование (если понадобится)

## 📝 План разработки

### Решения и допущения
- Основная БД — PostgreSQL; SQLite используется только как legacy-справка.
- Основная версия плана хранится в `docs/DEVELOPMENT_PLAN.md`.
- Источник истины для AI/TTS — `shared/core/` (после переноса из `core/`).
- Разработка ведётся через Docker (`docker-compose.dev.yml`), деплой — через `docker-compose.prod.yml`.

### Рекомендуемый старт и поэтапное решение

**Цель старта:** как можно раньше получить рабочий контур (Docker → API → БД → Mini App) и дальше расширять функционал.

1. **Скелет проекта и окружение (День 1)**
   - Базовая структура репозитория, `.env.example`, общий `.gitignore`.
   - Docker Compose для dev: PostgreSQL + API + Mini App (пустые приложения).
   - Проверка, что всё поднимается одной командой.

2. **БД и миграции (День 1–2)**
   - SQLAlchemy модели по текущей схеме.
   - Alembic и первая миграция (только структура таблиц/полей, без переноса данных).
   - Тест подключения и CRUD для одной сущности.

3. **Базовый API (День 2–3)**
   - Авторизация через Telegram (`WebApp.initData`).
   - Минимальные эндпоинты: `/users/me`, `/tales`, `/collection`.
   - Проверка доступа и простая бизнес-логика.

4. **Мини App каркас (День 3–4)**
   - React + Tailwind + Router + React Query.
   - Экран профиля и списка коллекции.
   - Интеграция с API и показ данных.

5. **Интеграция и генерация (День 4–7)**
   - Подключение `shared/core` для генерации и озвучки.
   - Эндпоинты генерации сказок.
   - UI для создания сказок и отображения результата.

6. **Стабилизация и подготовка к деплою (День 7+)**
   - Ошибки, логирование, CORS, healthchecks.
   - Docker prod, Nginx, базовые тесты.
   - Документация и инструкции запуска.

## 🔐 Безопасность

### Backend
- JWT токены с коротким временем жизни
- Refresh токены для обновления
- Валидация всех входных данных (Pydantic)
- SQL injection защита (SQLAlchemy ORM)
- Rate limiting (опционально)
- HTTPS только

### Frontend

## 📦 Хранение файлов

### Стратегия хранения аудиофайлов

**Development:**
- Локальное хранение в папке `audio_files/`
- Простая структура для разработки
- Файлы не коммитятся в git (в .gitignore)

**Production:**
- **Вариант 1:** Локальное хранение (только для начального этапа)
  - Папка `audio_files/` на сервере
  - Регулярные бэкапы
  - Ограничено размером диска сервера
  - Низкая латентность (~1-5 мс)
  
- **Вариант 2: Yandex Object Storage + CDN** ⭐ (рекомендуется)
  - **Производительность:**
    - С CDN: 10-50 мс латентность (первое обращение)
    - С CDN: ~10-30 мс (повторные обращения из кеша)
    - Без CDN: 50-200 мс (не рекомендуется для production)
  - **Преимущества:**
    - Автоматическое масштабирование
    - Резервное копирование встроено
    - Высокая доступность (99.9%+)
    - Интеграция с Yandex Cloud CDN
    - Оптимально для пользователей в России/СНГ
    - Подписанные URL для безопасного доступа
  - **Настройка:**
    - Создать bucket в Yandex Object Storage
    - Подключить Yandex Cloud CDN
    - Настроить CORS для доступа из Mini App
    - Использовать временные подписанные URL (TTL 1-24 часа)
  - **Регион:** Выбрать ближайший к основной аудитории (обычно ru-central1)

**Структура хранения:**
```
audio_files/ (в bucket)
├── users/
│   ├── {user_id}/
│   │   ├── {tale_id}_audio_{timestamp}.mp3
│   │   └── ...
│   └── ...
└── shared/  # Для случайных сказок
    ├── {tale_id}_audio_{timestamp}.mp3
    └── ...
```

**Доступ к файлам:**
- **Development:** Через API endpoint `/api/v1/audio/{tale_id}` (прокси через API)
- **Production (Yandex Object Storage):**
  - Временные подписанные URL (рекомендуется)
  - TTL: 1-24 часа для безопасности
  - Прямой доступ через CDN (быстрее)
  - Или через API endpoint с проксированием

**Рекомендации по оптимизации:**
1. Использовать CDN для всех аудиофайлов
2. Настроить кеширование на CDN (TTL 7-30 дней)
3. Прогрессивная загрузка для длинных аудио
4. Кеширование на клиенте (браузер)
5. Сжатие аудио (MP3 с оптимальным битрейтом)
